# 06 — Jobs & Sending Engine

> **Status:** design, authoritative for Phase 6. Elaborates §5 of
> `00-product-brief.md`.
> **Owns:** `worker/`, `src/modules/jobs/`, `src/modules/sending/`,
> `src/app/api/worker/tick/route.ts`.
> **Does not own:** `prisma/schema.prisma`. Every model here is defined by the
> schema doc; this document specifies the *SQL, ordering, and handler logic* that
> operate on it.

The queue and the sending engine are one document because they are one
mechanism. Sending is the queue's dominant workload, and every hard property the
product owes (no duplicates, no out-of-window sends, no cap breach) is a
property of how a job is leased, guarded, and committed — not of an email
library.

## 0. Conformance to the committed schema

`prisma/schema.prisma` landed while this document was being drafted and it is
authoritative. Names and conventions below follow it exactly. The differences
worth stating up front, because they invert a natural assumption:

| Fact in the schema | Consequence for this design |
|---|---|
| `Job.priority` — **higher runs first** | every `ORDER BY priority` is `DESC`. Sends outrank rollups by having a *bigger* number. |
| `Job.state`, not `status`; `Job.attempt`, not `attempts` | column names throughout §3–§7. |
| `JobState` includes `RETRYING`, distinct from `PENDING` | the lease predicate is `state IN ('PENDING','RETRYING')`. `RETRYING` is observability only. |
| `Job.dedupeKey` is **globally, unconditionally** `@@unique` | a recurring job's key must embed a period bucket. There is no "unique among outstanding rows" escape hatch. |
| `Job.id` is `BigInt @default(autoincrement())` | job ids are numeric; never interpolate one into JSON as a JS number without care. |
| `Job.workspaceId` is **non-null** | there are no system-global jobs. `MAINTENANCE` is enqueued per workspace. |
| `Job.scheduledEmailId` is a real FK | pause/cancel finds send jobs by FK, not by JSON extraction. |
| The mailbox model is **`EmailAccount`**; live status is `ACTIVE` | not `Mailbox`, not `CONNECTED`. |
| Enrollment is **`CampaignLead`**, `@@unique([campaignId, leadId])` | no re-enrollment cohort exists (§16 item 8). |
| `ScheduledEmail.state` values are `SCHEDULED SENDING SENT FAILED CANCELLED BOUNCED` | there is no `QUEUED` and no `NEEDS_RECONCILIATION` (§16 item 3). |
| `ScheduledEmail.rfcMessageId` is generated by us pre-send | it is the reconciliation key; there is no separate send token. |
| Content is frozen on `ScheduledEmail` (`subject`, `bodyHtml`, `bodyText`, `toEmail`, `sequenceVersion`) | the send handler renders nothing. Personalisation happens at materialisation. |
| Sending windows are `sendWindowStartMinute/EndMinute/Days` ints on **both** `Campaign` and `EmailAccount` | the window is an intersection, not a single owner (§9.2). |
| The cap counter is `MailboxDailyStat.sentCount`, keyed `(emailAccountId, localDate)` | there is no `reserved` column. This is the one place the schema cannot express the design safely; see §10.2 and §16 item 2. |
| Doc 09 names the liveness table `WorkerHeartbeat` and the entrypoint API `drainQueue()` | used verbatim here. |

Where this document needs something the schema does not yet have, it is listed
in §16 with a recommendation, not silently assumed.

## 1. What this design must prove

| Claim (brief §1) | Mechanism | Where |
|---|---|---|
| **A browser is never required** | all sending is initiated by `worker/index.ts`, a long-running Bun process. The web app only writes rows; no code path under `src/app/**` calls a provider. | §3 |
| **We never send the same email twice** | `@@unique([campaignLeadId, sequenceStepId])` + `@@unique([dedupeKey])`; a single-statement `SCHEDULED → SENDING` claim; a stable `rfcMessageId`; mandatory provider-side reconciliation before any retry of a `SENDING` row. | §6 |
| **We never send outside the window** | the window is re-evaluated inside the claim path, not only at materialisation. Out-of-window work is **deferred**, never dropped. | §9.4 |
| **We never exceed the daily cap** | a conditional single-statement counter increment taken *before* the provider call. | §10.2 |
| **A reply stops the sequence** | `PROCESS_INBOUND_MESSAGE` at higher priority than sends, plus a reply check inside the claim statement itself. | §12.2 |

Two rules run through everything:

1. **When in doubt, do not send.** A missed email is recoverable by a human; a
   duplicate is a burnt prospect and a spam complaint. Every ambiguous state
   resolves toward not sending.
2. **Jobs are retryable attempts; domain rows carry once-only semantics.** A
   `Job` is at-least-once by contract. `ScheduledEmail` is the fact that this
   lead gets this step exactly once. Conflating them is the classic bug in this
   kind of system.

## 2. Migration SQL this phase must add

The models exist. What is missing is the SQL Prisma cannot express, and it is
load-bearing rather than an optimisation. All of it belongs in one migration,
`prisma/migrations/*_jobs_engine_indexes/migration.sql`.

**Ownership.** Doc 01 §6 already defines two of these and this document does not
redefine them: `Job_leasable_idx` (partial, on `("runAt", "priority" DESC)`) and
`ScheduledEmail_due_idx` (partial, on `("scheduledAt")`). Use those names. The
indexes below are the ones no other doc claims.

One note on `Job_leasable_idx`: doc 01 orders it `("runAt", "priority" DESC)`
while the lease query (§4.2) orders `priority DESC, "runAt"`. Those disagree, so
the planner sorts rather than walking the index in order. The fix is one of the
two, not both — see §16 item 11. Everything else here is unaffected.

```sql
-- ── 1. Lease-expiry sweep.
CREATE INDEX IF NOT EXISTS job_lease_expiry_idx
  ON "Job" ("leaseExpiresAt")
  WHERE state = 'RUNNING';

-- ── 2. Dead-letter console, grouped by type.
CREATE INDEX IF NOT EXISTS job_dead_idx
  ON "Job" (type, "failedAt" DESC)
  WHERE state = 'DEAD';

-- ── 3. At most ONE outstanding scheduled email per enrollment. This is what
--       makes "materialise only the next step" safe, and it turns a
--       double-running scheduler from a data incident into a rejected INSERT.
CREATE UNIQUE INDEX IF NOT EXISTS scheduled_email_one_outstanding_uq
  ON "ScheduledEmail" ("campaignLeadId")
  WHERE state IN ('SCHEDULED', 'SENDING') AND "campaignLeadId" IS NOT NULL;

-- ── 4. Crash-recovery sweep: SENDING rows of unknown outcome.
CREATE INDEX IF NOT EXISTS scheduled_email_stuck_idx
  ON "ScheduledEmail" ("claimedAt")
  WHERE state = 'SENDING';

-- ── 5. Due-enrollment scan for the scheduler tick.
CREATE INDEX IF NOT EXISTS campaign_lead_due_idx
  ON "CampaignLead" ("nextStepAt" ASC)
  WHERE state IN ('ACTIVE', 'WAITING');
```

Index 3 (`scheduled_email_one_outstanding_uq`) is the single most valuable line in
the migration: it turns a double-running scheduler from a data incident into a
rejected `INSERT`. Review the lease and due queries with `EXPLAIN` and confirm no
sort node appears; if one does, the `ORDER BY` does not match the index and the
queue degrades under load rather than failing visibly.

### 2.3 Send-attempt forensics

A `SENDING` row tells us an attempt was in flight; it does not tell us what the
provider said, or when, or which worker asked. After a crash that is exactly
what we need, so it gets a table.

```prisma
model SendAttempt {
  id               String   @id @default(cuid())
  workspaceId      String
  scheduledEmailId String
  scheduledEmail   ScheduledEmail @relation(fields: [scheduledEmailId], references: [id], onDelete: Cascade)
  attemptNo        Int
  workerId         String
  startedAt        DateTime  @default(now()) @db.Timestamptz(6)
  finishedAt       DateTime? @db.Timestamptz(6)
  /// accepted | rejected | unknown | reconciled_duplicate | deferred
  outcome          String?
  providerMessageId String?
  providerStatus   Int?
  errorClass       String?
  errorMessage     String?

  @@unique([scheduledEmailId, attemptNo])   // a replayed job cannot double-log
  @@index([workspaceId, startedAt])
}
```

Cheap to write, and the difference between "we think it might have sent" and
"attempt 2 started 14:03:12 by worker-7, outcome unknown, rfcMessageId X".

## 3. Worker architecture

### 3.1 Process shape

```
                        ┌────────────────────────────────────┐
   Next.js app ──write──▶│           PostgreSQL 16            │
   (RSC / actions)      │ Job · ScheduledEmail · CampaignLead │
                        │ MailboxDailyStat · WorkerHeartbeat  │
                        └────────────────────────────────────┘
                                  ▲              ▲
                     lease/commit │              │ lease/commit
                        ┌─────────┴───┐    ┌─────┴────────┐
                        │  worker #1  │    │  worker #N   │  bun run worker
                        └─────┬───────┘    └─────┬────────┘
                              │                  │
                              ▼                  ▼
                        Gmail API · Anthropic API
```

The web app never runs a job inline. A server action that needs background work
inserts a `Job` row **in the same transaction** as the domain change that caused
it. That is the whole reason the queue lives in Postgres, and it is why "a
browser must be open" can never become true.

`POST /api/worker/tick` (§3.6) is an additional trigger for platforms with no
long-running process. Doc 09 recommends topology A (a real worker) and this
design assumes it; the tick path is a supported fallback, not the primary.

### 3.2 Files

```

  loop.ts         # drainQueue(): lease → run → commit
  maintenance.ts  # lease reclaim, recurring enqueue, stuck-send sweep, prune

```

**Not owned here.** `src/modules/mailboxes/providers/**` — the `MailProvider`
interface, `GmailProvider`, `FakeProvider`, MIME construction, and provider error
mapping — belongs to doc 05 §1.2. This module consumes it through
`getProvider()` from that module's public API and never imports `googleapis`
itself. Concretely: the send handler builds no MIME and parses no Gmail error; it
calls `provider.send(...)` and maps the returned `ProviderError` class to a
`JobOutcome`.

`worker/registry.ts` is the only place the worker touches domain code, and it
imports module public APIs exclusively — the brief's import rules apply to the
worker process too.

### 3.3 The main loop

```ts
// worker/index.ts
import '@/lib/env';                                   // validate or exit(1)

await assertSchemaCurrent();                          // doc 09 §3.2, or exit(1)

const workerId = `${hostname()}:${process.pid}:${randomHex(4)}`;
const log = logger.child({ workerId });
await jobsRepo.heartbeat(workerId, { leasedCount: 0, version: BUILD_SHA });
log.info({ event: 'worker.boot', pid: process.pid, version: BUILD_SHA });

let draining = false;
const inflight = new Map<bigint, Promise<void>>();
const aborts   = new Map<bigint, AbortController>();

for (const sig of ['SIGTERM', 'SIGINT'] as const) {
  process.on(sig, () => {
    if (draining) { log.warn({ event: 'worker.force_exit' }); process.exit(1); }
    draining = true;                                  // stop leasing NEW work
    log.info({ event: 'worker.draining', inflight: inflight.size });
  });
}

void maintenanceLoop(workerId, () => draining);       // §3.5, independent timer

let idleMs = env.WORKER_POLL_MIN_MS;                  // 250
while (!draining) {
  const free = env.WORKER_CONCURRENCY - inflight.size;
  if (free === 0) { await Promise.race(inflight.values()); continue; }

  const jobs = await jobsRepo.leaseBatch({ workerId, limit: free });

  if (jobs.length === 0) {
    // Jittered so N workers never poll in lockstep.
    await sleep(idleMs * (0.75 + Math.random() * 0.5));
    idleMs = Math.min(idleMs * 2, env.WORKER_POLL_MAX_MS);   // → 5s
    continue;
  }
  idleMs = env.WORKER_POLL_MIN_MS;

  for (const job of jobs) {
    const ac = new AbortController();
    aborts.set(job.id, ac);
    inflight.set(job.id, runOne(job, { workerId, signal: ac.signal, log })
      .finally(() => { inflight.delete(job.id); aborts.delete(job.id); }));
  }
}

// ── graceful shutdown: three phases, no job is ever lost ────────────────────
const deadline = Date.now() + env.WORKER_SHUTDOWN_GRACE_MS;      // 25_000
while (inflight.size > 0 && Date.now() < deadline) {
  await Promise.race([...inflight.values(), sleep(250)]);
}
for (const ac of aborts.values()) ac.abort();                    // cooperative stop
await Promise.race([Promise.allSettled([...inflight.values()]), sleep(3_000)]);

const stranded = [...inflight.keys()];
if (stranded.length) {
  // Release rather than let the lease expire: a deploy costs a 2s gap, not 2 min.
  await jobsRepo.releaseLeases(stranded, workerId);
  log.warn({ event: 'worker.stranded_released', count: stranded.length });
}
await jobsRepo.markStopped(workerId);
log.info({ event: 'worker.shutdown', reason: 'signal', inflight: stranded.length });
process.exit(0);
```

Three shutdown phases, none of which lose work:

* finishes naturally → committed normally;
* aborted cooperatively → handler returns `retry`, row goes back to `PENDING`;
* neither → `releaseLeases` resets it and **decrements `attempt`**, because a
  deploy is not the job's fault.

```sql
-- src/modules/jobs/repo.ts :: releaseLeases
UPDATE "Job"
SET state = 'PENDING', "runAt" = now(), "leaseExpiresAt" = NULL,
    "lockedBy" = NULL, "lockedAt" = NULL,
    attempt = GREATEST(attempt - 1, 0), "updatedAt" = now()
WHERE id = ANY($1::bigint[]) AND "lockedBy" = $2 AND state = 'RUNNING';
```

The `lockedBy = $2` predicate is a fencing token. If our lease had already
expired and a peer re-leased the job, we do not stomp its state.

### 3.4 `runOne` — the per-job wrapper

```ts
// src/modules/jobs/runner.ts
export async function runOne(job: JobRow, deps: RunDeps): Promise<void> {
  const def = registry[job.type];
  const parsed = def.schema.safeParse(job.payload);
  if (!parsed.success) {
    // Schema drift after a deploy is terminal on attempt 1: retrying a payload
    // the handler cannot parse just burns the budget and hides the bug.
    return applyOutcome(job, { kind: 'terminal', error: new BadPayloadError(parsed.error) });
  }

  const ac = deps.abortController;
  const renew = setInterval(async () => {
    const held = await jobsRepo.renewLease(job.id, deps.workerId, def.leaseSeconds);
    if (!held) { deps.log.error({ event: 'job.lease_lost', jobId: String(job.id) }); ac.abort(); }
  }, (def.leaseSeconds * 1000) / 3);                 // renew at 1/3 of the lease

  const startedAt = Date.now();
  try {
    const outcome = await withTimeout(def.handler(parsed.data, { job, ...deps }), def.timeoutMs);
    await applyOutcome(job, outcome, Date.now() - startedAt);
  } catch (err) {
    await applyOutcome(job, classifyError(err), Date.now() - startedAt);
  } finally {
    clearInterval(renew);
  }
}
```

Renewing at one third of the lease means two consecutive renewal failures still
leave slack before expiry, so a transient DB blip cannot cause a second worker to
start the same job. **A handler that loses its lease must stop**: for
`SEND_SCHEDULED_EMAIL` the signal is checked immediately before the provider call
and passed into the HTTP request so an in-flight call is aborted.

### 3.5 Maintenance loop

Runs every 30s in every worker. The mutating parts are serialised by a Postgres
advisory lock, so N workers do not duplicate them.

```ts
async function maintenanceTick(workerId: string) {
  await jobsRepo.heartbeat(workerId, { leasedCount: inflight.size, version: BUILD_SHA });

  // pg_try_advisory_lock returns immediately; only one worker proceeds.
  if (!(await jobsRepo.tryAdvisoryLock(MAINTENANCE_LOCK))) return;
  try {
    await jobsRepo.reclaimExpiredLeases();       // §4.5
    await jobsService.enqueueRecurring();        // §5.3 — the cron replacement
    await sendingService.sweepStuckSends();      // §6.5
    await jobsRepo.pruneTerminalJobs({ days: 30 });   // never prunes DEAD
  } finally {
    await jobsRepo.releaseAdvisoryLock(MAINTENANCE_LOCK);
  }
}
```

Liveness, per doc 09: a worker is **alive** if
`lastSeenAt > now() - interval '3 minutes'`. Zero alive workers with a non-empty
leasable queue is the most important alert in the system, because it is exactly
the shape of "campaigns silently stopped sending".

### 3.6 `POST /api/worker/tick`

Contract fixed by doc 09 §1.3; this document owns the implementation.

```ts
// src/app/api/worker/tick/route.ts
export async function POST(req: Request) {
  if (!timingSafeBearerEqual(req.headers.get('authorization'), env.WORKER_AUTH_TOKEN)) {
    return new Response(null, { status: 401 });
  }
  // Overlapping cron invocations are correct but double connection use; skip fast.
  return await withAdvisoryXactLock('worker-tick', async (got) => {
    if (!got) return Response.json({ skipped: 'already running' }, { status: 202 });
    const result = await drainQueue({
      workerId: `tick:${randomHex(6)}`, budgetMs: 50_000, maxJobs: 25,
    });
    return Response.json(result);   // { leased, succeeded, failed, deferred, ranForMs }
  });
}
```

`drainQueue` is the same lease/run/commit code as the loop, bounded by wall clock
and job count. It is concurrency-safe with real workers for free: `SKIP LOCKED`
does not care who is asking.

Honest limits, so nobody plans around a fantasy:

* Cron granularity is ~1 minute, so per-mailbox pacing finer than a minute cannot
  be honoured; sub-minute gaps degrade to bursts at the top of each minute, which
  is *worse* for deliverability than the pacing it replaces.
* No lease renewal happens between invocations, so a job whose handler outlives
  the invocation has its lease expire and gets retried.
* Therefore cron-only is for demo and low-volume deployments. Anything above a
  few hundred sends a day needs the real worker. This is a deployment
  constraint, not a TODO.

## 4. Job leasing

### 4.1 Why `FOR UPDATE SKIP LOCKED`

`SKIP LOCKED` tells Postgres: when a candidate row is already row-locked by
another transaction, ignore it and take the next one. That single behaviour gives
us the whole queue:

* **No coordination.** No leader, no partition assignment, no lock service.
  Adding worker #7 requires no configuration.
* **No convoy.** Plain `FOR UPDATE` would queue every worker behind the same
  head-of-queue row and serialise the fleet.
* **No lost work.** The lock is a *transaction* lock, so a worker that dies
  mid-transaction has it released by the server and the row is instantly visible
  to others.

`leaseExpiresAt` exists on top because the row lock lives only for the lease
transaction (milliseconds) while the job's execution takes seconds to minutes
outside any transaction — it makes HTTP calls. The row lock guarantees exactly
one worker flips the row to `RUNNING`; the lease timestamp guarantees the row
becomes available again if that worker dies mid-execution.

### 4.2 The lease statement

One statement, one round trip, atomic.

```sql
-- src/modules/jobs/repo.ts :: leaseBatch($1 workerId, $2 limit, $3 types|NULL, $4 leaseSecs)
WITH ready AS (
  SELECT id
  FROM "Job"
  WHERE state IN ('PENDING', 'RETRYING')
    AND "runAt" <= now()
    AND ($3::"JobType"[] IS NULL OR type = ANY($3))
  ORDER BY priority DESC, "runAt" ASC          -- higher priority first (§0)
  FOR UPDATE SKIP LOCKED
  LIMIT $2
)
UPDATE "Job" j
SET state            = 'RUNNING',
    attempt          = j.attempt + 1,
    "lockedBy"       = $1,
    "lockedAt"       = now(),
    "leaseExpiresAt" = now() + make_interval(secs => $4),
    "startedAt"      = COALESCE(j."startedAt", now()),
    "updatedAt"      = now()
FROM ready
WHERE j.id = ready.id
RETURNING j.*;
```

Review notes that matter:

* `FOR UPDATE SKIP LOCKED` must sit on a plain single-table `SELECT` inside the
  CTE. Postgres rejects it with aggregates, `DISTINCT`, or a `GROUP BY`.
* The statement may return **fewer than `LIMIT`** rows when locks are skipped.
  The loop treats that as normal, not as "queue empty".
* `ORDER BY priority DESC, "runAt" ASC` is identical to doc 01 §6.3's lease query,
  deliberately — there must be exactly one lease statement in the codebase. It does
  **not** match doc 01's `Job_leasable_idx` column order; see §16 item 11.
* There is no window in which a row is selected but not yet `RUNNING`.

### 4.3 Lease duration by duration class

| Class | `leaseSeconds` | `timeoutMs` | Job types |
|---|---|---|---|
| `fast` (<1s) | 60 | 15_000 | `MAINTENANCE`, `MAILBOX_RENEW_WATCH` |
| `normal` (1–10s) | 120 | 60_000 | `SEND_SCHEDULED_EMAIL`, `SCHEDULER_TICK`, `PROCESS_INBOUND_MESSAGE`, `PROCESS_WEBHOOK_EVENT`, `AI_*` |
| `slow` (10–120s) | 300 | 240_000 | `MAILBOX_SYNC`, `MAILBOX_BACKFILL`, `ROLLUP_ANALYTICS`, `LEAD_IMPORT_BATCH` |

`timeoutMs < 2 × leaseSeconds` and renewal at `leaseSeconds/3`, so a healthy
job's lease never expires while it works. The lease is a liveness signal, not a
deadline.

### 4.4 `attempt` increments on lease, not on failure

The non-obvious choice, and deliberate. If a handler OOM-kills the process, no
failure path runs — so a failure-time increment leaves the job retrying forever,
wedging the queue behind a poison job. Incrementing at lease time makes a crash
loop terminate at `maxAttempts` and land in the dead letter for a human. The cost
is that a clean shutdown would unfairly burn an attempt, which is why
`releaseLeases` decrements it (§3.3) and a deferral does not consume one (§7.2).

### 4.5 Reclaiming a dead worker's jobs

```sql
-- src/modules/jobs/repo.ts :: reclaimExpiredLeases
UPDATE "Job"
SET state = CASE WHEN attempt >= "maxAttempts" THEN 'DEAD' ELSE 'RETRYING' END,
    "runAt" = CASE WHEN attempt >= "maxAttempts" THEN "runAt" ELSE now() END,
    "failedAt" = CASE WHEN attempt >= "maxAttempts" THEN now() ELSE NULL END,
    "leaseExpiresAt" = NULL, "lockedBy" = NULL, "lockedAt" = NULL,
    "lastError" = 'LeaseExpired: worker presumed dead', "updatedAt" = now()
WHERE state = 'RUNNING' AND "leaseExpiresAt" < now()
RETURNING id, type, attempt, "maxAttempts", "scheduledEmailId";
```

**`SEND_SCHEDULED_EMAIL` must never be blindly retried by this path.** A
reclaimed send may already have been accepted by Gmail. The safety comes from the
handler, not from the reclaim: it sees `ScheduledEmail.state = 'SENDING'` and
routes into reconciliation (§6.4) instead of sending, and refuses to act until
`claimedAt` is older than the reconciliation grace period.

**Why this is safe with N workers.** At most one transaction holds the row lock
on a given `Job`, so at most one worker flips it `PENDING → RUNNING`; a second
either skips it (locked) or does not see it (already `RUNNING`). The only path to
two workers executing one job body is lease expiry, which requires the first to
be unresponsive for ≥ `leaseSeconds`. Every handler except the send is idempotent
by construction (§5.2), so that overlap is harmless — and the send is protected
at the domain layer by the claim in §6.2, which the second worker loses.

## 5. Job taxonomy

`JobType` is a committed Prisma enum with 16 values (§0). This design adds no
values; where a needed job has no enum member it is expressed as a `MAINTENANCE`
subtype, discriminated by `payload.task`. Adding an enum value is a migration, so
the taxonomy is deliberately conservative.

### 5.1 The registry type

```ts
// src/modules/jobs/types.ts
export type JobDefinition<T extends JobType> = {
  schema: z.ZodType<JobPayloadMap[T]>;
  handler: (p: JobPayloadMap[T], ctx: JobCtx) => Promise<JobOutcome>;
  /** HIGHER runs first (schema convention, §0). */
  priority: number;
  maxAttempts: number;
  leaseSeconds: number;
  timeoutMs: number;
  backoff: { baseMs: number; capMs: number };
  /** Pure function of the payload → Job.dedupeKey. Globally unique. */
  dedupeKey: (p: JobPayloadMap[T]) => string;
};

export const registry: { [T in JobType]: JobDefinition<T> };
```

Priority bands, in schema order (higher first):

| Priority | Meaning |
|---|---|

| 80 | inbound processing that can cause a stop |

| 50 | scheduling / enrollment |
| 30 | AI, imports |
| 10 | rollups, warmup, maintenance |

`MAINTENANCE` subtypes, discriminated by `payload.task`:

| `task` | Does |
|---|---|
| `prune_jobs` | deletes `SUCCEEDED`/`CANCELLED` older than 30d. **Never `DEAD`.** |

`reconcile_send` as a `MAINTENANCE` subtype rather than its own enum value is a
compromise forced by the committed enum. It is flagged in §16 item 4: it deserves a
real `JobType` because it is a correctness path, not housekeeping, and burying it
in `MAINTENANCE` makes it harder to alert on and to prioritise. Until then it is
enqueued with `priorityOverride: 90` so it still outranks sends.

### 5.3 Recurring enqueue — the cron replacement

No external scheduler. `enqueueRecurring()` runs inside the maintenance tick
under the advisory lock:

```ts
export async function enqueueRecurring(): Promise<void> {
  for (const c of await campaigns.repo.listTickable()) {           // ACTIVE/SCHEDULED, window near
    await enqueue({ type: 'SCHEDULER_TICK', workspaceId: c.workspaceId, payload: { campaignId: c.id } });
  }
  for (const w of await workspaces.repo.listActiveIds()) {
    await enqueue({ type: 'MAINTENANCE', workspaceId: w, payload: { task: 'prune_jobs' } });
    await enqueue({ type: 'MAINTENANCE', workspaceId: w, payload: { task: 'sweep_stuck_sends' } });
  }
  for (const m of await mailboxes.repo.listDueForWatchRenew()) {
    await enqueue({ type: 'MAILBOX_RENEW_WATCH', workspaceId: m.workspaceId, payload: { emailAccountId: m.id } });
  }
}
```

`enqueue` is `INSERT … ON CONFLICT ("dedupeKey") DO NOTHING`. Calling it every
30s while the minute bucket is unchanged is a no-op. No cron table, no "did I
already schedule this" bookkeeping, no drift.

`listTickable` returns campaigns that are `ACTIVE`, or `SCHEDULED` with
`startAt <= now()`, served by the committed `@@index([status, startAt])`.
`SCHEDULED → ACTIVE` is applied by the tick handler itself, so a launch time
passing needs no separate mechanism.

### 5.4 The enqueue API

```ts
// src/modules/jobs/index.ts
export type EnqueueInput<T extends JobType> = {
  type: T;
  workspaceId: string;                 // non-null, per the schema
  payload: JobPayloadMap[T];
  runAt?: Date;
  priorityOverride?: number;
  scheduledEmailId?: string;           // sets the FK for send jobs
  /** Enlist in a caller-owned transaction. THIS is why the queue is in Postgres. */
  tx?: Prisma.TransactionClient;
};

export async function enqueue<T extends JobType>(i: EnqueueInput<T>): Promise<{ jobId: bigint; created: boolean }>;
export async function enqueueMany(inputs: EnqueueInput<JobType>[], tx?: Prisma.TransactionClient): Promise<number>;
```

A unique violation (23505) on `dedupeKey` is **success**, not an error: it means
the work is already queued. The caller sees `created: false`.

`tx` is not a convenience. "Launch campaign" must write `Campaign.status='ACTIVE'`
and the first `SCHEDULER_TICK` in one transaction. With Redis that is a dual write
that can drift; here it cannot.

## 6. Idempotency and the crash-after-accept problem

### 6.1 The failure being designed against

```
 t0  worker leases SEND_SCHEDULED_EMAIL for row S
 t1  worker POSTs users.messages.send
 t2  Gmail accepts, queues for delivery, begins writing its 200 response
 t3  ✗ the worker dies (OOM / SIGKILL / partition). Nothing was written.
     S is still SENDING. No row records what happened.
 t4  the lease expires; a peer leases the job again
 t5  ??? if it sends, the prospect receives the same email twice
```

No transaction discipline fixes this, because the side effect is outside the
database. There are exactly two honest options: ask the provider what happened, or
never retry. We do the first and fall back to the second.

### 6.2 Ordering of operations

```
┌─ TX-A: one guarded statement ───────────────────────────────────────────────┐
│ 1. CLAIM  ScheduledEmail SCHEDULED → SENDING, attemptCount += 1,            │
│    claimedAt/claimedBy set — joined against Campaign, CampaignLead, Lead,    │
│    EmailAccount, Suppression, EmailMessage (the pre-send guard, §12.2).      │
│    0 rows ⇒ another worker owns it, or a stop condition fired ⇒ STOP.        │
│ 2. INSERT SendAttempt(scheduledEmailId, attemptCount, workerId)             │
│    unique(scheduledEmailId, attemptNo) ⇒ a replay cannot double-log.         │
└─────────────────────────────────────────────────────────────────────────────┘
┌─ TX-B: one statement each ──────────────────────────────────────────────────┐
│ 3. RESERVE cap: MailboxDailyStat reservedCount += 1 WHERE reserved < cap     │
│    0 rows ⇒ cap reached ⇒ release the claim, defer to the next window.       │
│ 4. CLAIM pacing slot: CAS on EmailAccount pacing column (§10.3)              │
│    0 rows ⇒ too soon ⇒ release claim + reservation, defer by the gap.        │
└─────────────────────────────────────────────────────────────────────────────┘
┌─ outside any transaction: the outside world ────────────────────────────────┐
│ 5. If attemptCount > 1, or the row was already SENDING on entry:             │
│      RECONCILE FIRST (§6.4). Found ⇒ jump to step 7 with the found ids.      │
│ 6. ctx.signal.throwIfAborted()      ← the last chance not to send            │
│    provider.send(frozen MIME + rfcMessageId + List-Unsubscribe)             │
└─────────────────────────────────────────────────────────────────────────────┘
┌─ TX-C: one transaction ─────────────────────────────────────────────────────┐
│  7. ScheduledEmail SENDING → SENT (providerMessageId, providerThreadId, sentAt)
│  8. SendAttempt.outcome = 'accepted', finishedAt = now()                     │
│  9. MailboxDailyStat.sentCount += 1                                          │
│ 10. EmailEvent(type = SENT)                                                  │
│ 11. CampaignLead: lastCompletedPosition = step.position, lastSentAt,         │
│     currentStepId = next, nextStepAt = computed, state = ACTIVE|WAITING      │
│ 12. enqueue the next SCHEDULER_TICK  — in this same transaction              │
└─────────────────────────────────────────────────────────────────────────────┘
```

Step 12 inside TX-C is the point of a Postgres queue: the fact that we sent and
the work to schedule the follow-up commit atomically. There is no window where a
send lands and the sequence forgets to continue.

Note the asymmetry: **the cap is reserved before the send and confirmed after.**
Incrementing only after would let a crash-after-accept under-count and breach the
cap. Reserving first can only over-count, i.e. under-send by one. That is the
safe direction, and it is the whole reason §2.1 adds `reservedCount`.

### 6.3 `rfcMessageId` — the reconciliation key

Generated by us at materialisation, per the schema's own comment, and stored
before any send:

```ts
scheduledEmail.rfcMessageId = `<${cuid()}.${scheduledEmail.id}@${sendingDomain}>`;
```

The outgoing MIME carries the headers doc 05 §6.6 defines — that document owns the
header set and this one consumes it:

```
Message-ID: <…@{mailbox domain}>          ← ours, committed pre-send
X-IM-Send-Token: <22-char base64url>      ← strategy B's match key
X-IM-Workspace:  <sha256(workspaceId)[0..16]>
List-Unsubscribe: <mailto:…>, <https://…>
List-Unsubscribe-Post: List-Unsubscribe=One-Click
```

`X-IM-Send-Token` is **derived, not stored**, resolving what doc 05 §6.6 flagged as
a conflict with an earlier draft of this file: there is no `sendToken` column and
none is needed.

```ts
// doc 05 §6.6 — reproducible during reconciliation, unguessable without the secret
sendToken(se) === base64url(hmacSha256(env.AUTH_SECRET, `send-token:v1:${se.id}`)).slice(0, 22)
```

Deriving it matters for reconciliation specifically: a random column would have to
be written before the send and read back after a crash, which is the same
bootstrapping problem the token exists to solve. An HMAC of the row id is
recomputable from the row alone, so reconciliation works even if nothing about the
attempt was persisted.

It is **stable across attempts**, not per attempt. That is the point: it is the
query key for asking the provider "did you already take this?".

To be unambiguous about what it does *not* do: a stable Message-ID does **not**
make the provider deduplicate. Gmail will happily accept two messages with the
same Message-ID and deliver both. The header enables *detection*, and detection
is what gates the retry.

Real constraint: **Gmail does not guarantee it preserves a caller-supplied
`Message-ID`.** In practice it usually does for `raw` MIME, but we do not rely on
it. Doc 05 §6.7 owns the send call and already reads the stored header back,
returning it as `SendResult.observedMessageId`; this document only consumes that
field. `rfcMessageId` is never overwritten with the observed value — it is the
key we will search by, and rewriting it would destroy the audit trail.

If `observedMessageId` differs from `rfcMessageId`, we log
`send.messageid_rewritten` once per mailbox per day and prefer strategy B below
for that mailbox from then on. The system adapts instead of silently becoming
unsafe.

### 6.4 Reconciliation

```ts
// src/modules/sending/reconcile.ts
export type ReconcileVerdict =
  | { kind: 'already_sent'; providerMessageId: string; providerThreadId: string }
  | { kind: 'not_sent' }
  | { kind: 'inconclusive'; reason: string };

export async function reconcileSend(
  ctx: Ctx, se: ScheduledEmailRow, provider: MailProvider,
): Promise<ReconcileVerdict>;
```

Strategy selection is driven by the provider's declared capabilities (doc 05 §3),
never by hardcoding Gmail: `capabilities.supportsMessageIdSearch` gates A,
`capabilities.preservesCustomHeaders` gates B, and `capabilities.messageIdFidelity`
plus any recorded rewrite downgrade decides which is primary.

**Strategy A — exact Message-ID lookup (primary).**
`provider.findByRfcMessageId(auth, se.rfcMessageId)` — an indexed, exact server-side
lookup, present iff `supportsMessageIdSearch`. One hit ⇒ `already_sent`. More than
one ⇒ we already double-sent at some point; return `already_sent` with the first and
log `send.duplicate_detected` at error level so it is investigated.

**Strategy B — bounded sent-folder scan** (fallback, and primary for mailboxes known
to rewrite `Message-ID`). List sent messages to `se.toEmail` since
`claimedAt - 10m`, capped at 25, then fetch each and match
`X-IM-Send-Token === sendToken(se)`. Unknown `X-` headers survive the send wherever
`preservesCustomHeaders` is true, which makes this the more robust signal; it is
secondary only because it costs more provider quota.

**If a provider supports neither** (`supportsMessageIdSearch` and
`preservesCustomHeaders` both false), reconciliation is impossible and the honest
consequence must be accepted rather than designed around: for that provider a send
whose outcome is unknown is **never retried**. It goes straight to the operator.
Doc 05 records these capabilities per provider precisely so this decision is data,
not a code branch someone forgets to add when SMTP lands.

**Strategy C — none.** If A and B cannot run (auth revoked, 5xx, quota
exhausted), the verdict is `inconclusive` and **we do not send.** The row stays
`SENDING`, `SendAttempt.outcome = 'unknown'`, and an operator decides. This is
the deliberate choice from §1: a stuck email beats a duplicate.

**The indexing-lag constraint.** Gmail's search index is not synchronous with the
send. A message accepted 3 seconds ago may not be findable by an exact id lookup yet,
and a naive immediate reconcile would answer `not_sent` and duplicate the email —
precisely the bug being prevented. Therefore:

```ts
const RECONCILE_GRACE_MS = 120_000;
// A SENDING row is not eligible for reconciliation until
//   claimedAt + RECONCILE_GRACE_MS < now()
```

A reclaimed send job whose row is `SENDING` and younger than the grace period
returns `defer(claimedAt + grace)` rather than reconciling.

### 6.5 The stuck-send sweep

```sql
SELECT id FROM "ScheduledEmail"
WHERE state = 'SENDING' AND "claimedAt" < now() - interval '120 seconds'
ORDER BY "claimedAt" LIMIT 200;
```

Each id gets a `MAINTENANCE{task:'reconcile_send'}` job at priority 90. This is
the safety net for the case where even the `Job` row is gone — cancelled by a
pause while `SENDING`, or pruned. Nothing can sit in `SENDING` indefinitely
without a human being told.

### 6.6 Retryable vs terminal classification

```ts
// src/lib/errors.ts
export class RetryableError extends AppError {}
export class TerminalError  extends AppError {}
export class DeferError     extends AppError {}   // not a failure at all
```

Gmail's raw error → `ProviderError` mapping is doc 05's `gmail-errors.ts` (a pure,
exhaustively tested function). What follows is **this** module's job: mapping a
`ProviderError` class to a queue outcome. The distinction matters — the provider
module decides *what went wrong*, the queue decides *what to do about it*.

```ts
// src/modules/sending/service.ts :: outcomeForProviderError
switch (true) {
  case status === 429:
  case status >= 500:
  case reason === 'quotaExceeded':
    return new RetryableError('gmail.rate_limited', { retryAfterHintMs: 15 * 60_000 });

  case status === 401:
    // One in-band refresh. If that fails the mailbox is genuinely broken.
    return refreshed ? new RetryableError('gmail.token_refreshed')
                     : new TerminalError('gmail.reauth_required', { setAccountStatus: 'DISCONNECTED' });

  case status === 403 && reason === 'domainPolicy':
    return new TerminalError('gmail.blocked_by_policy', { setAccountStatus: 'ERROR' });

  case status === 400 && /invalid (to header|recipient)/i.test(msg):
    return new TerminalError('gmail.invalid_recipient', { suppress: 'INVALID_EMAIL' });

  case status === 400 && /payload too large|exceeds/i.test(msg):
    return new TerminalError('gmail.message_too_large');

  case isNetworkError(err):
    // ⚠ OUTCOME UNKNOWN. This is NOT "not sent".
    return new RetryableError('gmail.unknown_outcome', { forceReconcileNextAttempt: true });

  default:
    return new RetryableError('gmail.unclassified');
}
```

The network case is the subtle one. A connection reset on the send call means we
do not know whether Gmail got it. It is retryable, but the retry **must**
reconcile first, which is what `forceReconcileNextAttempt` guarantees.

A `TerminalError` sets `ScheduledEmail.permanentFailure = true` and
`state = 'FAILED'`, matching the committed column's documented purpose.

**Gmail's real limits, stated plainly.** Gmail enforces a *rolling* send limit —
roughly 2 000/day for Workspace, 500 for consumer accounts, plus opaque
per-minute and per-recipient throttles — server-side, with no API to query it.
Our `dailySendLimit` (default 50) is therefore a courtesy limit set far below
Gmail's, not a mirror of it. A `quotaExceeded` from Gmail is treated as a hard
stop for that mailbox for the rest of the day: set
`EmailAccount.status = 'THROTTLED'` with `throttledUntil` at local midnight, so
the scheduler stops selecting it (the committed `@@index([status, throttledUntil])`
serves exactly this), and raise a deliverability alert.

## 7. Retries and the dead letter

### 7.1 Backoff — exponential with full jitter

```ts
// src/modules/jobs/backoff.ts  (pure, unit-tested)
export function nextDelayMs(attempt: number, p: { baseMs: number; capMs: number }, rnd = Math.random): number {
  const exp = Math.min(p.capMs, p.baseMs * 2 ** (attempt - 1));
  return Math.floor(rnd() * exp);            // FULL jitter: uniform over [0, exp)
}
```

Full jitter, not "exponential ± 20%". When Gmail rate-limits a mailbox, every one
of its queued sends fails within the same second. Equal-jitter retries reconverge
into the same thundering herd and get rate-limited again; full jitter spreads them
across the whole window on the first retry. Occasionally retrying sooner than the
nominal delay is irrelevant when the cap is hours wide.

A provider `Retry-After` or a `retryAfterHintMs` always wins:
`runAt = now() + max(hint, nextDelayMs(...))`.

`SEND_SCHEDULED_EMAIL` at `base 60s, cap 2h, maxAttempts 8` gives a worst-case
retry horizon of roughly 8 hours — long enough to outlast a Gmail rate-limit
window or a bad deploy, short enough that a human looks before a day is lost.

### 7.2 Outcome application

```ts
export type JobOutcome =
  | { kind: 'success'; result?: Json }
  | { kind: 'retry'; error: Error; retryAfterMs?: number }
  | { kind: 'terminal'; error: Error }
  | { kind: 'defer'; until: Date; reason: DeferReason }   // NOT a failure
  | { kind: 'cancelled'; reason: string };
```

```sql
-- retry (attempt was already incremented at lease time)
UPDATE "Job"
SET state = 'RETRYING', "runAt" = $2, "leaseExpiresAt" = NULL, "lockedBy" = NULL,
    "lockedAt" = NULL, "lastError" = $3, "lastErrorStack" = $4,
    "durationMs" = $5, "updatedAt" = now()
WHERE id = $1 AND "lockedBy" = $6 AND attempt < "maxAttempts";

-- when the above matches 0 rows because attempt >= maxAttempts
UPDATE "Job"
SET state = 'DEAD', "failedAt" = now(), "completedAt" = now(),
    "lastError" = $3, "lastErrorStack" = $4, "updatedAt" = now()
WHERE id = $1 AND "lockedBy" = $6;

-- defer: attempt is DECREMENTED. A closed window is not a failed attempt.
UPDATE "Job"
SET state = 'PENDING', "runAt" = $2, attempt = GREATEST(attempt - 1, 0),
    "leaseExpiresAt" = NULL, "lockedBy" = NULL, "lockedAt" = NULL, "updatedAt" = now()
WHERE id = $1 AND "lockedBy" = $6;
```

Every terminal write is guarded by `"lockedBy" = $6`. A worker whose lease expired
cannot overwrite the state of the worker that took over. This fencing predicate is
not optional.

**Deferral loop protection.** `Job` has no `deferrals` column, so the guard is
derived: a job whose `runAt` has been pushed forward more than 200 times is
indistinguishable from a healthy one by state alone. The check is therefore
`now() - createdAt > 14 days ⇒ terminal('DeferLoop')`, plus the `window.empty`
alert (§13.1). A misconfigured campaign — an empty `sendWindowDays`, or a cap of
zero — must look broken, because it is. §16 item 5 recommends adding the counter
column; the age-based fallback is the version that works with the schema as
committed.

### 7.3 Dead letter: inspection and replay

`DEAD` is a queryable state, not a separate table, and `prune_jobs` never deletes
it. The console at `/settings/system/jobs` (OWNER/ADMIN, workspace-scoped) groups
`DEAD` rows by `(type, lastError)` with counts, last occurrence, and a payload
sample with secrets redacted.

```ts
export async function replay(ctx: Ctx, jobIds: bigint[]): Promise<ReplayResult>;
export async function replayGroup(ctx: Ctx, sel: { type: JobType; limit: number }): Promise<ReplayResult>;
export async function discard(ctx: Ctx, jobIds: bigint[], note: string): Promise<void>;
```

Replay **resets the original row** rather than cloning it, because `dedupeKey` is
globally unique and a clone would collide:

```sql
UPDATE "Job"
SET state = 'PENDING', attempt = 0, "runAt" = now(), "failedAt" = NULL,
    "lastError" = NULL, "lastErrorStack" = NULL,
    "replayCount" = "replayCount" + 1, "updatedAt" = now()
WHERE id = ANY($1::bigint[]) AND state = 'DEAD' AND "workspaceId" = $2;
```

`replayCount` is the committed column that distinguishes "retried by the system"
from "a human pressed retry", and the `SendAttempt` rows preserve the failure
history that resetting the job row discards.

Replaying a dead `SEND_SCHEDULED_EMAIL` re-enters the handler at the claim in
§6.2, so a replay of an email that actually did go out is caught by
reconciliation, not sent again. **Replay is safe by construction, not by operator
discipline** — which is the only reason the button can exist.

`discard` requires a note and writes to `AuditLog` (brief §6).

## 8. The scheduler

### 8.1 Why we materialise rows rather than compute on the fly

Computing "who is due now" by walking `Campaign × Sequence × CampaignLead` on
every tick is tempting and wrong:

1. **There is nowhere to put the uniqueness.** `@@unique([campaignLeadId,
   sequenceStepId])` is the structural no-duplicate guarantee. A computed view has
   no row to constrain, so uniqueness would fall to application logic under
   concurrency — the exact class of bug we cannot afford.
2. **Content must be frozen.** The schema stores `subject`, `bodyHtml`, `bodyText`,
   `toEmail`, `variantId`, and `sequenceVersion` on the row precisely so a
   mid-flight template edit cannot rewrite a pending send and so the preview
   matches what was sent.
3. **The due query is one index scan** over a partial index (§2 index 4) instead
   of a multi-way join over every active enrollment.
4. **The UI can show the plan.** "Step 3 goes out Tuesday 09:12 from
   ops@acme.com" is a row we read, not a simulation we re-run.

The cost is real and accepted: rows must be invalidated when the plan changes.
We materialise **one step ahead** per enrollment — enforced by index 5 — so the
invalidation surface is a single row per enrollment.

### 8.2 From ACTIVE campaign to sent email

```
enqueueRecurring (every 30s, under the advisory lock)
   └─ for each tickable campaign → SCHEDULER_TICK{campaignId}

SCHEDULER_TICK
   │ if status = SCHEDULED and startAt <= now() → ACTIVE, launchedAt = now()
   │ if endAt is set and now() >= endAt → materialise nothing
   │
   ├─ (a) MATERIALISE: for each CampaignLead in (ACTIVE, WAITING) with
   │      nextStepAt <= now() + 15m and NO outstanding ScheduledEmail:
   │         step = next enabled step after lastCompletedPosition
   │         if none                → CampaignLead COMPLETED; continue
   │         if step.type = WAIT    → advance position, nextStepAt += delay; continue
   │         if step.type=CONDITION → evaluate; CONTINUE | SKIP_NEXT | STOP
   │         due  = (lastSentAt ?? startedAt ?? enrolledAt) + step.delayMinutes
   │         slot = nextOpenSlot(due, intersect(campaign, mailbox), tz)   ← §9
   │         render subject/body from the chosen variant, freeze them
   │         INSERT ScheduledEmail(state=SCHEDULED, scheduledAt=slot, …)
   │           ON CONFLICT DO NOTHING          -- both unique indexes protect us
   │
   ├─ (b) PROMOTE: for each SCHEDULED row with scheduledAt <= now() + 30s
   │         enqueue SEND_SCHEDULED_EMAIL{scheduledEmailId}   [same transaction]
   │
   └─ (c) if nothing advanced and no enrollment is advanceable
             → Campaign COMPLETED, completedAt = now()
```

Wait steps are **resolved, not scheduled**: a `WAIT` step never becomes a
`ScheduledEmail`, it only contributes `delayMinutes` to the next email step. A
7-day wait therefore costs zero rows and zero jobs — `nextStepAt` is simply in the
future and the tick's `WHERE` clause skips the enrollment.

Note that promotion does **not** change `ScheduledEmail.state`. The committed enum
has no `QUEUED`, so the row stays `SCHEDULED` until a worker claims it. The
`dedupeKey` on the send job is what prevents double promotion, and it is why that
key must be `SEND_SCHEDULED_EMAIL:{scheduledEmailId}` with no time bucket.

### 8.3 The two hot queries

```sql
-- (a) due enrollments — served by campaign_lead_due_idx
SELECT cl.*
FROM "CampaignLead" cl
WHERE cl."campaignId" = $1
  AND cl.state IN ('ACTIVE', 'WAITING')
  AND cl."nextStepAt" <= now() + interval '15 minutes'
  AND NOT EXISTS (
    SELECT 1 FROM "ScheduledEmail" se
    WHERE se."campaignLeadId" = cl.id AND se.state IN ('SCHEDULED', 'SENDING')
  )
ORDER BY cl."nextStepAt"
LIMIT 500;

-- (b) due scheduled rows — served by ScheduledEmail_due_idx (doc 01 §6)
SELECT id, "workspaceId"
FROM "ScheduledEmail"
WHERE state = 'SCHEDULED' AND "scheduledAt" <= now() + interval '30 seconds'
ORDER BY "scheduledAt"
LIMIT 500;
```

Both are index scans whose cost is proportional to the number of *due* rows, not
to table size — the reason both indexes are partial. A tick that hits either 500
limit re-enqueues itself with `runAt = now()`, so a 500k-lead campaign advances in
bounded chunks and never holds a long transaction.

The `+30 seconds` lookahead means the send job exists slightly before it is legal
to send. The window, cap, and pacing checks inside the handler are the real gate,
which is exactly why they live there.

## 9. Sending windows and timezones

### 9.1 Representation

The schema stores windows as integers on both `Campaign` and `EmailAccount`:
`sendWindowStartMinute`, `sendWindowEndMinute` (minutes from local midnight,
`[start, end)`), `sendWindowDays` (ISO weekdays, 1 = Monday), plus an IANA
`timezone` string on each.

```ts
// src/modules/sending/windows.ts
export type Window = { startMinute: number; endMinute: number; days: number[]; tz: string };

export function isWithinWindow(instant: Date, w: Window): boolean;
export function nextOpenSlot(from: Date, w: Window): Date;      // throws EmptyWindowError
export function intersectWindows(campaign: Window, mailbox: Window): Window | null;
```

Implemented with `Intl.DateTimeFormat.formatToParts` against the IANA database Bun
already ships. No date library, no hand-rolled offset table. `nextOpenSlot` scans
forward at most **14 days** and throws `EmptyWindowError` if it finds nothing —
that is a misconfiguration and must surface as a campaign validation error at
launch, not as a silently dead campaign.

### 9.2 Which window and which timezone win

The schema's own comment settles the window question: *"The campaign window
INTERSECTS each mailbox's window; the narrower of the two wins, so a mailbox can
never be pushed outside its own limits by a campaign setting."*

> **Rule.** The effective window is the intersection of the campaign's window and
> the assigned mailbox's window. Days intersect as a set; minutes intersect as a
> range. Each side is interpreted in **its own** timezone before intersecting, so
> the comparison happens on real instants, never on raw minute integers. An empty
> intersection is a launch-time validation error, never a silent no-send.
>
> The **mailbox's** timezone defines the calendar day for the daily cap
> (`MailboxDailyStat.localDate`), per the schema's comment on that column.

Justifications, since the choices are not interchangeable:

* **Intersection, not campaign-wins.** The cap and window on `EmailAccount` are
  reputation protection for a resource shared across campaigns. If a campaign
  setting could widen a mailbox's window, one careless campaign could push a
  mailbox into 3am sends and damage every other campaign using it.
* **Mailbox timezone for the cap.** A "daily" cap needs a day boundary, and the
  mailbox is the entity Gmail meters. If the boundary followed the campaign,
  two campaigns in two zones sharing one mailbox could each spend a full day's
  quota inside one Gmail day.
* **Lead timezone is not used.** `Lead` carries no timezone in the committed
  schema, so "9am in the prospect's morning" is not implementable and this
  document does not pretend otherwise. It is listed in §16 item 6 as a future option
  with the condition attached: only with a *known* IANA zone per lead, never
  guessed from country or area code, because a guessed zone makes the schedule
  unpredictable *and* wrong.

Intersecting minute integers across two different zones is the part implementers
get wrong. Do not compare `startMinute` values directly when the zones differ —
convert each window to concrete instants for the day under test, then intersect
those. The pure-function boundary in `windows.ts` exists to make that testable.

### 9.3 DST — the named failure modes

All storage is UTC (brief §9), so the only exposure is wall-clock → instant
conversion inside `nextOpenSlot`. Two concrete failures:

**Spring forward — the nonexistent local time.** In `America/New_York`,
2026-03-08 has no 02:30 local. A window covering it collapses. A naive
implementation that constructs `2026-03-08T02:30` and converts gets silently
shifted, and every subsequent computation that day lands an hour early — so a
whole day of sends goes out before the window opens. *Rule:* `nextOpenSlot` scans
forward in **real UTC minutes** and tests each candidate with `isWithinWindow`,
rather than constructing a local timestamp and converting it. A range entirely
inside the skipped hour simply yields no slot that day.

**Fall back — the ambiguous local time.** 2026-11-01 01:30 in `America/New_York`
occurs twice, EDT then EST. A wall-clock-first implementation can emit both, so an
hourly-paced campaign sends a **double batch** in that hour, breaching pacing and
possibly the cap. The same forward-scan-in-UTC rule fixes it: distinct UTC instants
are each considered exactly once regardless of how they are labelled locally.

Third-order effect, accepted: on the spring-forward day the window is an hour
shorter, so the day's cap may not be fully spent. We under-send by up to one
hour's pacing, once a year, in one direction. Not worth engineering around.

`tests/unit/sending/windows.test.ts` must be table-driven over `America/New_York`
(2026-03-08, 2026-11-01), `Europe/London` (2026-03-29, 2026-10-25),
`Australia/Sydney` (southern-hemisphere reversal), and `Asia/Kolkata` (a +05:30
offset, to catch anything assuming whole hours).

### 9.4 Deferral, not dropping

The send handler's first checks, before any provider contact:

```ts
const w = intersectWindows(campaignWindow(campaign), mailboxWindow(account));
if (!w) return { kind: 'terminal', error: new EmptyWindowError(campaign.id) };

if (!isWithinWindow(new Date(), w)) {
  const next = nextOpenSlot(new Date(), w);
  await sending.repo.reschedule(se.id, next);      // row stays SCHEDULED
  return { kind: 'defer', until: next, reason: 'outside_window' };
}
```

A deferral sets `Job.runAt` forward, returns the row to `PENDING`, and
**decrements `attempt`** (§7.2) — a closed window must not consume the retry
budget. `ScheduledEmail.scheduledAt` moves; nothing is deleted.

Nothing is ever dropped for being out of window. That is the difference between
"sends resume Monday 09:00" and "Friday's leads silently never got step 2".

## 10. Rate limiting, caps, and pacing

### 10.1 The three independent limits

| Limit | Scope | Source | On breach |
|---|---|---|---|
| Daily cap | mailbox × mailbox-local day | `EmailAccount.dailySendLimit`, and `Campaign.dailySendLimit` as an extra ceiling | defer to the next window slot |
| Minimum gap | mailbox | `minSecondsBetweenSends` + `sendJitterSeconds` | defer by the remaining gap |
| Provider quota | mailbox, opaque | reactive: 429 / `quotaExceeded` | `status = THROTTLED`, `throttledUntil` = local midnight |

All three are per **mailbox**, never per campaign. The mailbox is what has a
reputation and what Gmail meters. Two campaigns sharing a mailbox share its cap,
and the UI must show that: "ops@acme.com — 47/50 today, 2 campaigns".

### 10.2 Atomic cap reservation

The entire cap enforcement is one statement. A `SELECT` then `UPDATE` races and
over-sends, so application code never reads the count to decide.

```sql
-- src/modules/sending/repo.ts :: reserveSendSlot($1 accountId, $2 localDate, $3 cap, $4 wsId)
INSERT INTO "MailboxDailyStat" ("id","workspaceId","emailAccountId","localDate",
                               "reservedCount","sentCount","createdAt","updatedAt")
VALUES ($5, $4, $1, $2, 1, 0, now(), now())
ON CONFLICT ("emailAccountId", "localDate") DO UPDATE
  SET "reservedCount" = "MailboxDailyStat"."reservedCount" + 1,
      "updatedAt" = now()
  WHERE "MailboxDailyStat"."reservedCount" < $3      -- ← the cap, same statement
RETURNING "reservedCount";
```

Zero rows ⇒ the cap is reached ⇒ defer. Postgres holds a row lock for the duration
of the `ON CONFLICT DO UPDATE`, so with 50 workers racing on one mailbox the
increments serialise and **exactly `cap` of them succeed**. `$3` is recomputed per
attempt from §10.4, so a warmup step-up or an operator change takes effect
immediately.

Release when the send does not happen:

```sql
UPDATE "MailboxDailyStat"
SET "reservedCount" = GREATEST("reservedCount" - 1, "sentCount"), "updatedAt" = now()
WHERE "emailAccountId" = $1 AND "localDate" = $2;
```

`GREATEST(..., sentCount)` makes the release idempotent and preserves
`reservedCount >= sentCount` even if it runs twice. Release is best-effort: a
worker that dies before releasing leaks one unit of quota for that day.
Under-sending by one is acceptable; over-sending is not.

`localDate` is the calendar date in the **mailbox's** timezone, computed once at
claim time and reused for the release so a send that straddles local midnight
cannot release a different day's reservation.

**Why `sentCount` alone cannot do this.** Incrementing `sentCount` after a
successful send means the check has to read it *before* the provider call, leaving
a window in which N workers all read `sentCount = cap-1` and all send. Bumping
`sentCount` before the send instead makes it a lie — it would count messages that
were never accepted, and analytics reads that column. Two different questions
("how much quota is committed" vs "how many actually went out") need two columns.
That is why §2.1 adds `reservedCount`. If it is refused, see §16 item 2.

### 10.3 Pacing and jitter

```ts
// src/modules/sending/pacing.ts
export function computeGapMs(a: {
  minSecondsBetweenSends: number; sendJitterSeconds: number;
  effectiveCap: number; windowMinutesToday: number;
}, rnd = Math.random): number {
  // Spread the day's cap across the day's open window, then floor at the configured minimum.
  const spread = (a.windowMinutesToday * 60_000) / Math.max(a.effectiveCap, 1);
  const base   = Math.max(a.minSecondsBetweenSends * 1000, spread);
  return Math.round(base + rnd() * a.sendJitterSeconds * 1000);
}
```

The jitter shape is the schema's, not an invention: `minSecondsBetweenSends` plus
a uniform draw from `[0, sendJitterSeconds]`, exactly as that column documents.
The `spread` term is the addition — it stops a 50-cap mailbox emptying its quota
in the first 75 minutes of an 8-hour window, which is the single
highest-leverage deliverability behaviour in the engine.

The slot claim is a compare-and-swap on the mailbox row:

```sql
-- src/modules/sending/repo.ts :: claimPacingSlot($1 accountId, $2 gapMs)
UPDATE "EmailAccount"
SET "nextSendAt" = now() + make_interval(secs => $2 / 1000.0), "updatedAt" = now()
WHERE id = $1 AND ("nextSendAt" IS NULL OR "nextSendAt" <= now())
RETURNING "nextSendAt";
```

Zero rows ⇒ another worker holds the slot ⇒ release the cap reservation and defer
by the remaining gap plus a small random offset, so the losers do not all retry on
the same instant.

`EmailAccount.nextSendAt` does not exist in the committed schema — `throttledUntil`
is a different concept (provider cooldown, not pacing). §16 item 1 requests the column.
Without it, pacing has to be derived from `lastSentAt + gap`, which does **not**
work: `lastSentAt` is only written *after* a successful send, so N workers claiming
concurrently all see the same stale value and all pass. The CAS needs a column it
can write *before* the send. This is the one gap that cannot be worked around
without weakening a guarantee.

**Order is fixed: cap first, then pacing.** The cap is the scarcer resource, and a
pacing loss releases the reservation on the way out. Reversing it would hold
pacing slots while discovering the cap is spent, stalling the mailbox for a whole
gap per rejected send.

Honest note: pacing and jitter make traffic less obviously automated. They do not
make cold email deliverable. Domain authentication, list quality, content, and
reply rate dominate by an order of magnitude, and the UI must not imply that a
pacing setting is a deliverability fix.

### 10.4 Warmup ramp for new mailboxes

```ts
const RAMP = [5, 10, 15, 22, 30, 40, 50, 65, 80, 100, 120, 140, 160, 180] as const;

export function effectiveCap(a: {
  dailySendLimit: number; warmupStatus: WarmupStatus; warmupStartedAt: Date | null; timezone: string;
}, campaignLimit: number | null, now = new Date()): number {
  const hard = Math.min(a.dailySendLimit, campaignLimit ?? a.dailySendLimit);
  if (a.warmupStatus !== 'ACTIVE' || !a.warmupStartedAt) return hard;
  const day = daysBetweenInTz(a.warmupStartedAt, now, a.timezone);
  return Math.min(hard, RAMP[Math.min(day, RAMP.length - 1)]);
}
```

Day 0 is 5 messages; the configured limit is reached around day 14.
`warmupStartedAt` is set on the first successful send, not on connect — a mailbox
connected and left idle for a month is still cold. A hard-bounce rate above 5%
over the last 7 days freezes the ramp at the current step; above 10% halves the
effective cap and raises a deliverability alert.

The ramp is a guardrail, not science. Inbox providers judge reputation on
engagement, not on our table. It prevents the worst mistake — a brand-new mailbox
sending 200 cold emails on day one — and is presented as exactly that.

## 11. State machines

### 11.1 Campaign — `CampaignStatus`

```
   ┌────────┐  launch(startAt)  ┌───────────┐  startAt reached  ┌────────┐
   │ DRAFT  ├──────────────────▶│ SCHEDULED ├──────────────────▶│ ACTIVE │
   └───┬────┘                   └─────┬─────┘  (SCHEDULER_TICK) └───┬────┘
       │  launch now                  │ unschedule                  │
       └──────────────────────────────┼─────────────────────────────┤ pause
                                      ▼                             ▼
                                 ┌────────┐                    ┌────────┐
                                 │ DRAFT  │                    │ PAUSED │
                                 └────────┘                    └───┬────┘
                                                        resume ────┘
   ACTIVE ──all enrollments terminal──▶ COMPLETED
   DRAFT | SCHEDULED | PAUSED | COMPLETED ──archive──▶ ARCHIVED
```

| From | To | Trigger | Who | Side effects |
|---|---|---|---|---|
| DRAFT | SCHEDULED | `launch(startAt)` | OWNER/ADMIN/MEMBER | validate (§11.4); set `startAt` |
| DRAFT | ACTIVE | `launch()` now | OWNER/ADMIN/MEMBER | validate; `launchedAt = now()`; enqueue `SCHEDULER_TICK` **in the same tx** |
| SCHEDULED | ACTIVE | `startAt <= now()` | `SCHEDULER_TICK` | `launchedAt = now()` |
| SCHEDULED | DRAFT | `unschedule()` | OWNER/ADMIN | cancel the pending tick |
| ACTIVE | PAUSED | `pause()` | OWNER/ADMIN/MEMBER | §11.3 |
| ACTIVE | PAUSED | no `ACTIVE` mailbox remains | system | §11.3 + notify |
| PAUSED | ACTIVE | `resume()` | OWNER/ADMIN/MEMBER | §11.5 |
| ACTIVE | COMPLETED | no advanceable enrollment | `SCHEDULER_TICK` | `completedAt = now()`; final `ROLLUP_ANALYTICS` |
| non-ACTIVE | ARCHIVED | `archive()` | OWNER/ADMIN | cancel all outstanding jobs + rows; read-only after |

Rejected with `InvalidTransitionError`: `ACTIVE → DRAFT`; `ACTIVE → ARCHIVED`
(pause first — deliberate friction, so archiving cannot silently abandon
in-flight sends); `COMPLETED → ACTIVE` (duplicate the campaign instead); anything
out of `ARCHIVED`.

`endAt` is not a state. It is a materialisation guard: `SCHEDULER_TICK` creates no
row at or after `endAt`, and the campaign reaches `COMPLETED` naturally once
outstanding rows drain.

### 11.2 Enrollment — `EnrollmentState` on `CampaignLead`

```
 PENDING ──first step materialised──▶ ACTIVE ◀────────┐
                                        │             │ next step due
                                        ├──▶ WAITING ─┘
                                        │
        ┌───────────────────────────────┼──────────────────────────┐
        ▼            ▼          ▼       ▼         ▼                ▼
     REPLIED      BOUNCED  UNSUBSCRIBED STOPPED  FAILED        COMPLETED
     (terminal)                        (stopReason)          (all steps sent)
                                        │
                             campaign paused → PAUSED ──resume──▶ ACTIVE|WAITING
```

`WAITING` is the state during a `WAIT` step or an out-of-window period; `ACTIVE`
means a step is due or in flight. Both are advanceable, which is why the due query
(§8.3) matches on both.

The terminal states map to `EnrollmentStopReason` as committed:
`REPLIED` ← `HUMAN_REPLY`; `BOUNCED` ← `HARD_BOUNCE` / `SOFT_BOUNCE_LIMIT`;
`UNSUBSCRIBED` ← `UNSUBSCRIBED` / `SPAM_COMPLAINT`; `STOPPED` ← `MANUAL`,
`SUPPRESSED`, `CONDITION_EXIT`, `LEAD_DISQUALIFIED`, `CAMPAIGN_DELETED`,
`DUPLICATE_ENROLLMENT`; `FAILED` ← `NO_ELIGIBLE_MAILBOX`, `INVALID_EMAIL`.

Terminal is terminal. `@@unique([campaignId, leadId])` means a lead cannot be
re-enrolled in the same campaign, so "email this lead again" is a new campaign
(§16 item 8).

### 11.3 Pause — nothing leaks out after it

The requirement most implementations get wrong. Pause is enforced at four layers,
and the last one is why the first three being individually sufficient does not
matter.

```
pause(campaignId) — ONE transaction:
  1. UPDATE "Campaign" SET status='PAUSED', "pausedAt"=now()
       WHERE id=$1 AND status='ACTIVE';            -- 0 rows ⇒ InvalidTransition
  2. UPDATE "CampaignLead" SET state='PAUSED', "updatedAt"=now()
       WHERE "campaignId"=$1 AND state IN ('ACTIVE','WAITING');
  3. UPDATE "ScheduledEmail"
       SET state='CANCELLED', "cancelledAt"=now(), "cancelledReason"='MANUAL'
       WHERE "campaignId"=$1 AND state='SCHEDULED';
       -- deliberately NOT 'SENDING': that one is already at the provider.
  4. UPDATE "Job" SET state='CANCELLED', "completedAt"=now()
       WHERE state IN ('PENDING','RETRYING')
         AND ( "scheduledEmailId" IN (SELECT id FROM "ScheduledEmail" WHERE "campaignId"=$1)
               OR (type='SCHEDULER_TICK' AND payload->>'campaignId' = $1) );
COMMIT
```

Layer 4 uses the committed `Job.scheduledEmailId` FK for send jobs — no JSON
extraction, and the committed `@@index([scheduledEmailId])` serves it. Only the
tick needs a JSON predicate, and it is low-cardinality enough not to warrant an
expression index.

Layer 3 sets `cancelledReason = 'MANUAL'` because the committed
`EnrollmentStopReason` enum has no `CAMPAIGN_PAUSED` member. That conflation is
ugly: it makes "an operator paused the campaign" indistinguishable from "an
operator stopped this lead", and the two behave differently on resume. §16 item 7
requests `CAMPAIGN_PAUSED`. Until then, resume distinguishes them by
`CampaignLead.state = 'PAUSED'` rather than by the reason on the row.

**Layer 4 is the pre-send guard** (§12.2), which re-reads campaign status inside
the claim statement. It catches the one case the transaction cannot: a worker that
leased the send job *before* the pause committed and is now, milliseconds later,
about to call Gmail. That job row was `RUNNING`, so step 4 above did not touch it.
The guard is what makes "no sends after pause" true rather than merely likely.

A job already past the guard **will** complete its send. That is correct, and must
be surfaced honestly: *"Paused. Up to N messages already handed to the provider may
still be delivered."* Claiming otherwise would be a lie, and un-sending does not
exist.

### 11.4 Launch validation

`launch()` refuses, with field-level errors, unless: ≥1 enabled `EMAIL` step;
every email step has ≥1 variant with non-empty subject and body; ≥1 `ACTIVE`
`EmailAccount` assigned via `CampaignMailbox`; ≥1 `CampaignLead`; a valid IANA
`timezone`; `sendWindowDays` non-empty; `sendWindowStartMinute < sendWindowEndMinute`;
a **non-empty intersection** with every assigned mailbox's window (§9.2); every
personalisation token either resolves for the assigned leads or has an explicit
fallback; and a workspace unsubscribe mechanism configured.

Failing fast here is what prevents the `EmptyWindow` and defer-loop classes of
silent breakage. A campaign that cannot send should refuse to launch, not launch
and do nothing.

### 11.5 Resume — restore in place, never re-insert

`@@unique([campaignLeadId, sequenceStepId])` is unconditional, so a cancelled row
can never be replaced by a fresh `INSERT`. Resume **restores in place**:

```sql
-- src/modules/campaigns/repo.ts :: restoreOnResume($1 campaignId, $2 newScheduledAt)
WITH restorable AS (
  SELECT se.id
  FROM "ScheduledEmail" se
  JOIN "CampaignLead" cl ON cl.id = se."campaignLeadId"
  JOIN "SequenceStep" st ON st.id = se."sequenceStepId"
  WHERE se."campaignId" = $1
    AND se.state        = 'CANCELLED'
    AND cl.state        = 'PAUSED'      -- NOT a lead that replied while paused
    AND st.enabled      = true
    AND NOT EXISTS (                    -- so index 5 cannot be violated
      SELECT 1 FROM "ScheduledEmail" o
      WHERE o."campaignLeadId" = se."campaignLeadId"
        AND o.state IN ('SCHEDULED','SENDING')
    )
  FOR UPDATE OF se SKIP LOCKED
)
UPDATE "ScheduledEmail" se
SET state = 'SCHEDULED', "cancelledAt" = NULL, "cancelledReason" = NULL,
    "scheduledAt" = $2, "updatedAt" = now()
FROM restorable WHERE se.id = restorable.id
RETURNING se.id, se."campaignLeadId";
```

Three details that are not optional:

* **Enrollment state is re-checked.** A lead who replied during the pause is
  `REPLIED`, and its row must stay `CANCELLED` forever. Resume is the single most
  likely moment to email someone who already answered, because the operator's
  mental model is "carry on where we left off" while the world moved on.
* **`rfcMessageId` is NOT regenerated.** It is the reconciliation key. A restored
  row that was briefly `SENDING` before the pause must keep the identity the
  provider may already have seen.
* **`scheduledAt` is recomputed** to `nextOpenSlot(now)`, so a campaign paused for
  a week resumes into the next open window instead of firing a week of backlog at
  once.

Ordering on resume, one transaction: `Campaign.status = 'ACTIVE'`; `CampaignLead`
`PAUSED → ACTIVE|WAITING` by whether `nextStepAt <= now()`; run the statement
above; enqueue `SCHEDULER_TICK`. The tick afterwards fills in any enrollment with
no outstanding row at all, so restore and materialise are complementary and
neither has to handle the other's case.

Sequence edits use the same mechanism: cancel the affected `SCHEDULED` row, and
the next tick re-materialises it against the new `sequenceVersion`. Already-sent
steps are frozen and an edit to a sent step is rejected.

## 12. Stop conditions

### 12.1 The catalogue

| Reason (`EnrollmentStopReason`) | Detected by | Propagation | Enrollment | Suppression |
|---|---|---|---|---|
| `HUMAN_REPLY` | `PROCESS_INBOUND_MESSAGE` | cancel outstanding rows for this enrollment; if `stopOnReplyAnyCampaign`, for every campaign | `REPLIED` | no |
| `HARD_BOUNCE` | bounce parsing (DSN, SMTP 5.x.x) | cancel for that lead in **every** campaign | `BOUNCED` | yes, `HARD_BOUNCE` |
| `SOFT_BOUNCE_LIMIT` | repeated soft bounces past a threshold | cancel this enrollment | `BOUNCED` | no |
| `UNSUBSCRIBED` | one-click link, `List-Unsubscribe-Post`, or classified reply intent | cancel for that address workspace-wide | `UNSUBSCRIBED` | yes, `UNSUBSCRIBED` |
| `SPAM_COMPLAINT` | complaint feedback where available | as unsubscribed + deliverability alert | `UNSUBSCRIBED` | yes, `SPAM_COMPLAINT` |
| `SUPPRESSED` | address already on the suppression list at claim time | cancel this row | `STOPPED` | already there |
| `MANUAL` | operator action; also campaign pause (§11.3) | cancel this enrollment | `STOPPED` / `PAUSED` | no |
| `CONDITION_EXIT` | a `CONDITION` step with outcome `STOP` | cancel this enrollment | `STOPPED` | no |
| `LEAD_DISQUALIFIED` | operator or AI scoring | cancel this enrollment | `STOPPED` | no |
| `NO_ELIGIBLE_MAILBOX` | every assigned mailbox is not `ACTIVE` | cancel outstanding rows | `FAILED` | no |
| `INVALID_EMAIL` | provider rejects the recipient | cancel; mark `permanentFailure` | `FAILED` | yes, `INVALID_EMAIL` note |
| `CAMPAIGN_DELETED` | campaign soft-deleted | cancel everything | `STOPPED` | no |
| `DUPLICATE_ENROLLMENT` | `skipIfInOtherCampaign` and the lead is in another ACTIVE campaign | never materialise | `STOPPED` | no |

A soft bounce is **not** a stop: it counts toward `SOFT_BOUNCE_LIMIT` and the next
step proceeds normally.

**Auto-replies are not replies.** An out-of-office must not stop a sequence, or
every European August kills every campaign. `PROCESS_INBOUND_MESSAGE` classifies
before stopping: headers first (`Auto-Submitted: auto-replied`, `X-Autoreply`,
`Precedence: bulk`, `X-Auto-Response-Suppress`), which is deterministic and free,
then `AI_CLASSIFY_MESSAGE` as advisory only. When classification is genuinely
uncertain we **stop and flag for review** — the asymmetry from §1: a wrongly
stopped sequence costs one follow-up; a wrongly continued one emails someone who
already answered.

Note the schema knob: `Campaign.stopOnReply` defaults true and
`stopOnReplyAnyCampaign` defaults false. The second being off by default is
correct — it would otherwise be a surprising cross-campaign side effect — but it
means a lead who replies to campaign A can still receive campaign B. That is a
product decision to surface in the UI, not a bug to fix in the engine.

### 12.2 The pre-send guard — one statement, the last line of defence

A reply can land in the seconds between promotion and the provider call. So the
claim is not a bare state flip; it is a join that re-verifies every stop condition
atomically with the transition.

```sql
-- src/modules/sending/repo.ts :: claimForSend($1 scheduledEmailId, $2 workerId)
WITH candidate AS (
  SELECT se.id
  FROM "ScheduledEmail" se
  JOIN "Campaign"     c  ON c.id  = se."campaignId"
  JOIN "CampaignLead" cl ON cl.id = se."campaignLeadId"
  JOIN "Lead"         l  ON l.id  = se."leadId"
  JOIN "EmailAccount" ea ON ea.id = se."emailAccountId"
  WHERE se.id    = $1
    AND se.state = 'SCHEDULED'            -- SENDING ⇒ reconcile path, not here
    AND c.status = 'ACTIVE'               -- pause / archive / complete
    AND c."deletedAt" IS NULL
    AND (c."endAt" IS NULL OR now() < c."endAt")
    AND cl.state IN ('ACTIVE','WAITING')  -- reply / bounce / unsub / manual stop
    AND l."deletedAt" IS NULL             -- lead deleted
    AND ea.status = 'ACTIVE'              -- mailbox disconnected / throttled / paused
    AND (ea."throttledUntil" IS NULL OR ea."throttledUntil" <= now())
    AND ea."deletedAt" IS NULL
    AND NOT EXISTS (                      -- suppression: address AND domain scope
      SELECT 1 FROM "Suppression" s
      WHERE s."workspaceId" = se."workspaceId"
        AND ( (s.scope = 'EMAIL'  AND s.value = lower(se."toEmail"))
           OR (s.scope = 'DOMAIN' AND s.value = split_part(lower(se."toEmail"), '@', 2)) )
    )
    AND NOT EXISTS (                      -- a human reply since this enrollment started
      SELECT 1 FROM "EmailMessage" m
      WHERE m."campaignLeadId" = cl.id
        AND m.direction = 'INBOUND'
        AND m."isAutoReply" = false
        AND m."receivedAt" > COALESCE(cl."startedAt", se."createdAt")
    )
  FOR UPDATE OF se SKIP LOCKED
)
UPDATE "ScheduledEmail" se
SET state = 'SENDING', "attemptCount" = se."attemptCount" + 1,
    "claimedAt" = now(), "claimedBy" = $2, "updatedAt" = now()
FROM candidate WHERE se.id = candidate.id
RETURNING se.*;
```

Zero rows is a normal, expected outcome for a stopped lead — not an error. The
handler then asks why, cheaply, and records it:

```ts
const claimed = await repo.claimForSend(se.id, workerId);
if (!claimed) {
  const why = await repo.diagnoseNotClaimable(se.id);   // StopReason | 'in_progress_elsewhere'
  if (why === 'in_progress_elsewhere') return { kind: 'cancelled', reason: why };
  await repo.cancel(se.id, why);
  await enrollments.stop(se.campaignLeadId, why);        // idempotent
  return { kind: 'cancelled', reason: why };
}
```

The `EmailMessage` anti-join is deliberately redundant with `cl.state`. Reply
processing is asynchronous: if the inbound row is written but the enrollment stop
has not been applied yet (its job is queued behind ours), the enrollment still
reads `ACTIVE` — and this subquery catches it anyway. Priority 80 vs 60 makes the
race rare; this clause makes it harmless.

Two cross-module dependencies, flagged in §16 item 9: `EmailMessage.direction`,
`isAutoReply`, `receivedAt`, and `campaignLeadId` must exist with these names, and
that anti-join wants `@@index([campaignLeadId, direction, receivedAt])`.

The suppression subquery does two exact lookups rather than a `LIKE`, which is
what the schema's own comment on `Suppression.value` prescribes. Note it matches
against `se.toEmail` (the frozen recipient), not `l.email` — if the lead's address
was corrected after materialisation, the row is cancelled and re-materialised
rather than retargeted, per that column's documented behaviour.

### 12.3 Where each check lives — and why the duplication is intentional

```
                    materialise   promote   claim/guard   provider
campaign paused          ✓           ✓           ✓           —
human reply              ✓           —          ✓✓           —
unsubscribed             ✓           —           ✓           —
suppression              ✓           —           ✓           —
mailbox not ACTIVE       ✓           —           ✓           —
sending window           ✓           —           ✓           —
daily cap                —           —           ✓           —
pacing gap               —           —           ✓           —
```

Checking at materialisation is an optimisation: it avoids creating doomed rows.
Checking at claim time is the **correctness** boundary, because it is the only
check that cannot be raced — it lives in the same statement that authorises the
send. If one column of this table had to be deleted, delete the first.

### 13.2 Answering "why has this lead not received step 3?"

This gets asked weekly, by a non-engineer, and the answer must not require SQL.

```ts
// src/modules/jobs/index.ts
export type LeadStepDiagnosis = {
  campaign: { id: string; name: string; status: CampaignStatus; pausedAt: Date | null };
  enrollment: { id: string; state: EnrollmentState; lastCompletedPosition: number;
                nextStepAt: Date | null; stopReason: EnrollmentStopReason | null; stoppedAt: Date | null };
  steps: Array<{
    position: number; type: SequenceStepType; enabled: boolean;
    state: 'sent' | 'scheduled' | 'sending' | 'cancelled' | 'failed' | 'bounced' | 'not_reached';
    scheduledAt?: Date; sentAt?: Date; cancelledReason?: EnrollmentStopReason;
    attempts?: Array<{ attemptNo: number; startedAt: Date; outcome: string | null; errorClass: string | null }>;
  }>;
  job: { id: string; state: JobState; runAt: Date; attempt: number;
         maxAttempts: number; lastError: string | null; replayCount: number } | null;
  mailbox: { id: string; email: string; status: EmailAccountStatus; throttledUntil: Date | null;
             sentToday: number; reservedToday: number; effectiveCap: number };
  window: { tz: string; openNow: boolean; nextOpenAt: Date | null; intersectionEmpty: boolean };
  verdict: string;    // one plain-English sentence
};

export async function diagnoseLeadStep(
  ctx: Ctx, args: { campaignId: string; leadId: string; position?: number },
): Promise<LeadStepDiagnosis>;
```

`verdict` comes from a decision list, evaluated in order, first match wins:

```
 1. enrollment terminal            → "Stopped {date}: {stopReason}."
 2. campaign PAUSED                → "Campaign paused {date}; step 3 was cancelled and will be
                                      rescheduled on resume."
 3. campaign COMPLETED/ARCHIVED    → "Campaign {status}; no further steps will send."
 4. mailbox not ACTIVE             → "Mailbox {email} is {status}; reconnect it to resume."
 5. window intersection empty      → "The campaign and mailbox sending windows do not overlap.
                                      Nothing can send until one is changed."
 6. ScheduledEmail SENDING > grace → "We could not confirm whether this was sent; awaiting
                                      reconciliation. It will not be re-sent automatically."
 7. job DEAD                       → "Sending failed permanently after {attempt} attempts:
                                      {lastError}. Replay from the jobs console."
 8. ScheduledEmail FAILED          → "Permanently failed: {lastError}."
 9. cap exhausted today            → "Mailbox {email} hit its daily cap ({sentToday}/{cap});
                                      next attempt {nextOpenAt}."
10. window closed now              → "Outside the sending window ({tz}); scheduled {scheduledAt}."
11. scheduledAt in the future      → "Not due yet; scheduled {scheduledAt}."
12. lastCompletedPosition < 3      → "Still on step {n}; step 3 is not due until step {n} sends
                                      and its {delayMinutes}m wait elapses."
13. fallthrough                    → "No blocking condition found — this is a bug. jobId {id},
                                      row state {state}."
```

Case 13 matters. An unexplained state must be reported as a bug, not papered over
with "processing". The lead timeline UI renders this structure directly, so the
support answer and the engineering answer are the same object.

## 14. Failure modes

| # | Failure | Blast radius | Detection | Recovery |
|---|---|---|---|---|
| 1 | Worker killed mid-job | its jobs stall ≤ `leaseSeconds` | stale `WorkerHeartbeat`; `job.lease_reclaimed` | `reclaimExpiredLeases` → `RETRYING`; sends route via reconcile (§6.4) |
| 2 | **Crash after Gmail accepted, before commit** | one email could duplicate | row stuck `SENDING` past grace; `send.unknown_outcome` | reconcile by exact Message-ID lookup, then `X-IM-Send-Token`; found ⇒ `SENT`; inconclusive ⇒ stays `SENDING` for a human, **never auto-sent** |
| 3 | All workers down | **no campaign sends at all** | `workers_alive == 0 AND jobs_leasable > 0` → page | restart; nothing is lost, `runAt` is in the past, backlog drains subject to cap and pacing |
| 4 | Postgres unavailable | everything halts | connection errors; health check fails | jobs are durable on disk; the loop resumes. Enqueue failures surface as action errors, never silent drops |
| 5 | Gmail 429 / `quotaExceeded` | that mailbox stalls | `mailbox.throttled_by_provider` | full-jitter backoff; `status=THROTTLED`, `throttledUntil` = local midnight; other mailboxes unaffected |
| 6 | Refresh token revoked | mailbox dead | 401 surviving one refresh | `status=DISCONNECTED`; its rows cancelled `NO_ELIGIBLE_MAILBOX`; campaigns with no other ACTIVE mailbox auto-pause; operator notified |
| 7 | Poison payload after a deploy | one job type stops | `job.dead` with `BadPayload` | terminal on attempt 1 (no wasted retries); fix the handler, `replayGroup` |
| 8 | Clock skew between workers | premature reclaim ⇒ double execution | rising `job.lease_reclaimed` with healthy heartbeats | **all queue time comes from Postgres `now()`, never a worker's clock.** Skew is structurally excluded; `Date.now()` is only used for local timers |
| 9 | Gmail push subscription lapses | replies undetected ⇒ **we keep emailing people who replied** | no `MAILBOX_SYNC{push}` for a mailbox in 2h | `MAILBOX_RENEW_WATCH` daily, plus an unconditional 15-minute poll sync per ACTIVE mailbox. Push is an optimisation; polling is the guarantee |
| 10 | `users.watch` 7-day expiry | as #9 | renewal job dead-letters | daily renewal, 5 attempts; a dead renewal raises a deliverability alert |
| 11 | Sequence edited mid-flight | plan drift | `sequenceVersion` mismatch | sent steps frozen; affected `SCHEDULED` rows cancelled and restored against the new version (§11.5); editing a sent step is rejected |
| 12 | Two campaigns share a mailbox and both hit the cap | one starves | `cap.exhausted` with 2 campaigns | accepted: the cap is per mailbox by design. FIFO by `runAt` is the fairness rule; per-campaign quota splitting is deliberately not built (§15) |
| 13 | Empty window intersection, or cap 0 | job defers forever | `window.empty`; age-based defer-loop guard (§7.2) | launch validation (§11.4) should prevent it; the guard makes it visible if it slips |
| 14 | Timezone data differs web vs worker | preview disagrees with reality | UI shows a different time than `scheduledAt` | one Bun version from one lockfile; the **authoritative** value is the stored `scheduledAt`, which the UI renders rather than recomputes |
| 15 | DST spring-forward inside the window | window an hour shorter; under-send | `cap_utilisation` dip, once a year | accepted (§9.3) |
| 16 | `Job` table growth | index bloat, slower leases | table size, autovacuum lag | partial indexes tie lease cost to leasable count; `prune_jobs` removes terminal rows >30d; `DEAD` retained |
| 17 | Open tracking blocked by the client | opens undercounted | systematically low open rate | not a bug and not fixable. Opens are labelled indicative (brief §10). **Never** gate a sequence condition on `HAS_OPENED_ANY` alone |
| 18 | Duplicate Gmail push for one message | duplicate processing | — | `WebhookEvent.providerEventId @unique` plus the job `dedupeKey`; handlers are idempotent anyway |
| 19 | Cron-only deployment falls behind | bursty pacing, growing backlog | `oldest_pending_job_age_sec` climbing | documented limitation (§3.6); run the real worker above a few hundred sends/day |
| 20 | Mixed worker versions during a rollout | inconsistent handler behaviour | `WorkerHeartbeat.version` differs | payloads are zod-validated and a handler must tolerate the previous release's payload for one deploy cycle |
| 21 | `reservedCount` leaked by a crash | under-send by ≤1 per crash | `reservedCount > sentCount` at day end | self-heals at the local-day boundary (a new row). A nightly `MAINTENANCE` reconcile clamps stale rows |

## 15. Configuration, tests, and what is deliberately not built

### 15.1 Worker environment

Additions to `.env.example` (names only), zod-parsed at worker start; the process
exits non-zero on anything missing or invalid. `WORKER_CONCURRENCY` and
`WORKER_AUTH_TOKEN` already exist.

```
WORKER_LEASE_SECONDS="120"
WORKER_POLL_MIN_MS="250"
WORKER_POLL_MAX_MS="5000"
WORKER_SHUTDOWN_GRACE_MS="25000"
WORKER_MAINTENANCE_INTERVAL_MS="30000"
WORKER_JOB_TYPES=""              # empty = all; else a comma list, for dedicated pools
SEND_RECONCILE_GRACE_MS="120000"
```

Concurrency of 4 (the existing default) is right. Nearly every job is IO-bound on
an external API, and per-mailbox pacing means more in-process concurrency does not
raise throughput — it only increases the number of workers losing the pacing CAS
and deferring. Scale by adding **processes** when there are many mailboxes, not by
raising this number.

regardless of what else works.

### 15.3 Deliberately not built

Each is a real feature in mature products and each is wrong for v1.

* **Per-campaign quota splitting inside a mailbox.** Fair-share across campaigns
  needs a weighted scheduler and a fairness ledger. FIFO by `runAt` is fair enough
  and is one `ORDER BY`.
* **Priority aging.** Static bands plus FIFO within a band starves nothing at our
  volumes, because sends dominate and share one band.
* **`LISTEN`/`NOTIFY` wakeups.** Would cut idle latency from ~250ms to ~1ms for
  work whose deadlines are minutes to days. Adds a persistent connection and a
  missed-notification recovery path (`NOTIFY` is not durable) for zero product
  benefit. Jittered polling is the boring right answer.
* **A separate dead-job table.** A state value plus a partial index gives the same
  queries without moving rows at the worst possible moment.
* **Cron expressions.** Three fixed cadences (30s maintenance, minute buckets,
  daily) cover every recurring need. A cron parser is a dependency and a class of
  "why didn't it fire" bugs in exchange for flexibility nobody asked for.
* **Workflow DAGs.** The one real chain (send → tick → send) is expressed by
  enqueueing the next job inside the committing transaction.
* **Retrying a send more than 8 times.** After ~8 hours a human should look.
  Retrying for days hides a broken mailbox behind a healthy-looking queue.
* **Open/click-gated branching as a default.** The schema exposes
  `HAS_OPENED_ANY` and `stopOnOpen`; both are off by default and stay that way,
  because pixel tracking is unreliable enough (§14 #17) that branching on it
  produces confidently wrong sequences.

## 16. Conflicts and gaps for the lead engineer

Ordered by how much they block. Items 1–3 change guarantees; the rest are
ergonomics or future scope.

1. **`EmailAccount` needs a pacing column (blocking, §10.3).** The per-mailbox
   minimum-gap CAS must write a "next eligible send" timestamp *before* the
   provider call. `lastSentAt` is written only after success, so N concurrent
   workers all read the same stale value and all pass the gap check — the gap is
   then unenforced under exactly the conditions it exists for. `throttledUntil` is
   a different concept (provider cooldown) and reusing it would make an operator
   pause look like a provider throttle. **Request:** add
   `nextSendAt DateTime? @db.Timestamptz(6)` to `EmailAccount`.

2. **`MailboxDailyStat` needs `reservedCount` (blocking, §2.1/§10.2).** Enforcing
   a cap atomically requires a counter that increments *before* the send;
   `sentCount` must remain a truthful record of accepted sends because analytics
   reads it. Without a second column the choice is a race (check-then-send) or a
   lie (count sends that never happened). **Request:** the `ALTER TABLE` in §2.1.
   If it is refused, the fallback is a `SERIALIZABLE` transaction around
   check-and-send, which serialises every send on one mailbox and turns cap
   enforcement into a throughput ceiling — worse, but not incorrect.

3. **`ScheduledEmail` has no state for "outcome unknown" (§6.4).** Reconciliation
   can end inconclusive, and such a row must be visible and excluded from retry.
   Today it stays `SENDING`, which is indistinguishable from "a worker is working
   on it right now" except by `claimedAt` age. That works — the sweep uses the
   grace period — but it means the UI has to explain a scary state with a
   timestamp comparison. **Request (nice to have):** a `NEEDS_RECONCILIATION`
   value in `ScheduledEmailState`. Not blocking; the age-based rule is sound.

4. **`JobType` has no `RECONCILE_SEND` (§5.2).** It is currently a `MAINTENANCE`
   subtype, which buries a correctness path in housekeeping and makes it harder to
   alert on and prioritise. **Request:** add the enum value.

5. **`Job` has no deferral counter (§7.2).** A job legitimately deferred hundreds
   of times (closed window over a long weekend) is indistinguishable from one
   spinning on a misconfiguration, except by row age. The age-based guard works
   but is coarse. **Request (nice to have):** `deferCount Int @default(0)`.

6. **`Lead` has no timezone (§9.2).** So "send at 9am in the prospect's morning"
   is not implementable and this document does not claim it. If it is wanted later,
   the condition is a *known* IANA zone per lead with an explicit
   campaign-level opt-in, falling back to the campaign zone when absent. Guessing
   from country or area code is worse than not personalising, because it makes the
   schedule unpredictable *and* wrong.

7. **`EnrollmentStopReason` has no `CAMPAIGN_PAUSED` (§11.3).** Pause currently
   writes `MANUAL` to `ScheduledEmail.cancelledReason`, conflating "the operator
   paused the campaign" (restorable) with "the operator stopped this lead"
   (terminal). Resume works around it by keying on `CampaignLead.state = 'PAUSED'`,
   but the audit trail is misleading. **Request:** add `CAMPAIGN_PAUSED`, and
   ideally `SEQUENCE_EDITED`.

8. **No re-enrollment is possible (§11.2).** `@@unique([campaignId, leadId])` means
   a lead can be in a campaign at most once, ever. That is a good default (it is
   the first line of defence against duplicate sends) but it makes "run this
   sequence again next quarter" a campaign duplication, not a re-enrollment. I
   recommend keeping the constraint and documenting duplication as the answer,
   rather than adding a cohort column that weakens the strongest guarantee in the
   schema. Flagging so the product side knows.

9. **Cross-module field contract with the inbox doc (§12.2).** The pre-send guard
   depends on `EmailMessage.campaignLeadId`, `.direction`, `.isAutoReply`, and
   `.receivedAt`. If those land under different names the guard must be updated in
   lockstep, and it wants `@@index([campaignLeadId, direction, receivedAt])`.
   Requesting they be treated as a fixed contract.

10. **Window intersection ownership (§9.2).** The schema puts a window on both
    `Campaign` and `EmailAccount` and its comment says the narrower wins, which is
    what this design implements. Worth confirming the UI presents it that way
    ("effective window: Mon–Fri 09:00–16:00, narrowed by ops@acme.com"), because an
    operator who sets a campaign window and sees no sends will otherwise file a bug.

11. **`Job_leasable_idx` column order disagrees with the lease query (§2, §4.2).**
    Doc 01 §6 defines the index as `("runAt", "priority" DESC)`, while doc 01 §6.3's
    own lease query — and this document's, deliberately identical — orders
    `priority DESC, "runAt"`. The planner cannot walk that index in the query's
    order, so it sorts the matched set on every poll by every worker. Not incorrect,
    but it forfeits the reason the index exists. **Recommendation:** change the
    index to `("priority" DESC, "runAt")`, since priority is the leading sort key and
    reordering the query instead would let a low-priority rollup jump ahead of a
    send. One-line fix, worth making before there is volume.

12. **Two documents now contain the lease SQL (§4.2 and doc 01 §6.3).** They agree
    today. They will not stay agreed if either is edited alone, and a divergence here
    is a correctness bug that no test would obviously catch. **Recommendation:** doc
    01 keeps it as the schema-level illustration, this document owns the
    implementation in `src/modules/jobs/repo.ts`, and there is exactly one such
    function in the codebase — every worker and the tick endpoint call it.
